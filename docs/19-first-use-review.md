# 처음 사용하는 사람 관점의 사용성 검토

2026-11-12 · 휴대폰 0.6.2 · 개선 제안이며 앱 기능 변경은 하지 않음.

## 검토 방식과 한계

개발 지식을 완전히 지운 실제 신규 사용자 실험은 아니다. 설명서를 읽지 않고 “수원월드컵경기장에 짐을 가져간다”는 상황에서 화면 문구와 버튼만 보고 판단하는 인지적 워크스루다. 이번에 테스트 가상 기기의 앱 데이터를 초기화하고 첫 실행→지도 진입→위치 권한 요청을 확인했다. 가상 기기의 System UI/Messages 응답 지연이 발생해 사진 촬영부터 전달까지 새로 완주하지 못했다. 시스템 앱 오류를 챙겨가의 오류로 집계하지 않는다.

근거 표기: **이번 실행** / **이전 실행 화면**(0.6.2 검증 기록 및 저장 화면) / **코드 확인** / **사용자 보고** / **예상 혼란**을 구분한다. 실제 휴대폰 카메라·실차 전송·실외 GPS는 이번 검토 결과가 아니다.

## 우선 개선할 순서

1. **장소명 검색과 선택 정보 보존**: 경기장·병원·마트 이름으로 찾고 장소명이 방문지에 남게 한다. 현재 네이버 지도 SDK 연결만으로 해결된 상태가 아니다.
2. **방문지와 짐 수정**: 별명 변경, 방문지 삭제, 짐 이동, 짐 없는 방문지를 지원한다.
3. **진행 흐름 정리**: 현재 할 일 중심으로 구성하고 단계 이동/완료 조건을 일관되게 만든다.
4. **폰·차량 백그라운드 도착 알림 구현**: 차량 연결을 기본으로 유지하고, 앱 화면을 닫아도 양쪽에서 알리도록 한다. 이는 문구 개선이 아닌 기능 구현 요구다. 장소명 검색과 함께 핵심 우선 과제로 다룬다.
5. **외출 완료와 삭제 분리**: 사용자가 기록을 잃을 것으로 예상하지 못하는 동작을 없앤다.

## 제안하는 첫 사용 흐름

어디로 가나요? → 장소명 검색 → 결과의 장소명·주소 확인 → 별명 선택(건너뛰기 가능) → 이곳에 가져갈 짐 촬영/짐 없음 → 다른 방문지 추가 또는 준비 확인 → 짐별 적재 확인 → 차량 연결·전송 확인 → 앱 화면을 닫아도 폰·차량에서 도착 알림 → 방문지별 전달 확인 → 외출 완료·기록 보관.

검색부터 막히는 현재 상태에서는 메뉴 장식보다 장소명 검색과 저장 정보부터 고치는 것이 우선이다. 장소 검색 공급자나 API 선정은 별도 조사·결정 사항이며 이 문서는 특정 서비스의 업체명 검색을 구현했다고 주장하지 않는다.

## 사용자 피드백 반영: 차량 중심과 백그라운드 도착 알림

폰은 차량용 앱의 준비·연결을 돕는 동반 앱이다. 폰 단독 사용 분기는 개선안에서 제외한다.

도착 알림의 목표는 앱 화면이 닫히거나 화면이 잠기고 다른 앱을 사용 중이어도 폰과 차량 양쪽에서 필요한 짐을 안내하는 것이다. 현재 구현은 이 목표를 충족하지 못한다. 다음은 구현 시 별도로 설계·검증해야 하며, 이미 구현됐다는 뜻이 아니다.

- 방문지·짐과 알림 상태를 차량과 공유해 폰 연결이 끊긴 경우의 동작을 정의한다.
- 폰의 백그라운드 도착 감지와 알림, 차량의 도착 이벤트 수신·알림을 각각 구현한다.
- 양쪽 알림이 같은 방문지와 짐을 가리키도록 하고 재진입 시 반복 알림 정책을 정한다.
- 화면 잠금·다른 앱 사용·프로세스 종료·연결 끊김을 구분해 검증한다. OS의 사용자 강제 종료 등 플랫폼 제약은 별도 확인하며 이를 일반적인 화면 닫기와 혼동하지 않는다.
- 차량에서는 주행 중 사진·확인 조작을 강요하지 않고, 차량 UX 제한에 맞는 안내와 정차 후 확인으로 연결한다.
