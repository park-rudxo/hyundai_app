# 1. 무엇을 언제까지 보여줘야 하는가

2026년 11월 3일 기준. 현대차·기아는 외부 개발자가 Pleos에서 구현할 차량용 앱을 모집한다. 분야는 열려 있다. 운전자나 동승자가 반복해서 겪는 한 장면과 그때 차량에서만 얻을 수 있는 가치를 설명하는 것이 출발점이다. [1–3]

## 지난 부산 아이디어 공모와 이번 개발 공모의 차이

11월 4일 공식 안내 대조. 두 대회 모두 운전자·동승자가 차에서 원하는 경험을 묻는다. 차이는 그 경험을 누가 어디까지 구현하고 어떤 근거로 평가받는가에 있다. [2, 3, 6]

| 비교 | 부산모빌리티쇼 고객 아이디어 공모 | 이번 차량용 앱 개발 공모 |
|---|---|---|
| 참가자가 만드는 것 | 관람객이 원하는 카라이프를 입력하면 현장에서 AI가 앱 화면 이미지를 생성 | 참가자가 Pleos용 앱을 기획하고, 2차 진출 시 실제 동작하는 앱을 직접 제출·시연 |
| 심사 | 창의성 50%, 실현 가능성 30%, 공감도 20%. 공감도에 현장 투표 반영 | 1차는 차량특화성·창의성·기술 활용성·사업성. 세부 배점 비공개. 수상작과 순위는 2차 제출·시연 결과로 확정 |
| 선정 이후 | 현대차가 아이디어의 개발·출시 가능성을 검토 | 선정팀은 전시용 APK를 준비하고 현장 시연. 마켓 입점은 별도 검증 대상 |

**개인 참가에 적용할 기준.** 불편 해소와 즐거움 모두 출발점이 될 수 있다. 구독 유지 가설을 택한다면 기획서에는 누가 언제 다시 쓸지를 쓰고, 시연에서는 실제 차량 입력이 달라질 때 결과가 달라지는 장면 하나를 보여준다. 앱 자체의 유료화나 구독 결제 기능은 공고의 필수 제출 요건에 없다. [1–3]

## 1차 심사 기준 분석

**공식 안내.** 설명회에서 제시한 모빌리티·라이프, 엔터테인먼트, 안전·동승자 케어는 분야 예시다. 기획 흐름은 운전자 또는 동승자가 원하는 경험에서 출발해 차량 상태·이동 상황·하드웨어와 연결하고, 이를 앱에서 구현하는 순서다. 1차 서류심사는 아래 네 항목을 모두 평가하며 세부 배점은 비공개다. [1, 2]

| 항목 | 주최 측이 보는 것 | 기획서에서 답할 질문 · 우리 해석 | 근거로 쓸 수 있는 자료 · 팀 제안 |
|---|---|---|---|
| 차량특화성 | 모바일 대비 독자적 가치, 주행·정차 및 차량 기능과의 결합 | 같은 사람이 같은 일을 휴대폰으로 할 때와 비교해 어느 순간 무엇이 달라지는가? | 동일 장면의 전후 흐름. 입력 횟수, 제공 시점, 동승자와의 역할 분담 등 실제 달라진 한 가지를 표시한다. |
| 창의성 | 운전자·동승자의 필요와 문제 정의, 해결 방식의 독창성과 명확성 | 기존 순정 기능·앱·사용자 습관으로 해결하고도 무엇이 남는가? 제안한 방식은 그 부분을 어떻게 해결하는가? | 최근 실제 경험 한 건과 가장 가까운 대안의 사용 흐름을 비교한다. 편의 개선뿐 아니라 새롭게 즐기고 싶은 경험도 조사 대상이다. |
| 기술 활용성 | Pleos Playground SDK·API를 핵심 기능과 사용 경험에 적절히 활용하는 정도 | 어떤 값을 받으면 앱의 판단이나 출력이 어떻게 달라지고, 사용자에게 그 차이가 보이는가? | 실제 입력 → 판단 조건 → 화면·소리·동작을 한 줄로 잇는다. API 문서 확인, 에뮬레이터 실측, 모의 입력을 구분한다. |
| 사업성 | 타깃의 명확성, 사용자 확보, 지속 이용과 서비스 확대 가능성 | 첫 사용자가 어디서 앱을 발견하고 어떤 계기에 다시 여는가? 같은 필요를 가진 다음 고객은 누구인가? | 첫 고객군·유입 경로·반복 상황을 적는다. 예상 MAU는 대상 규모와 이용률 가정을 밝히고, 재이용률은 처음 사용한 집단 중 어떤 기간에 다시 쓴 비율인지 정의한다. |

**기준을 혼동하기 쉬운 지점.** 차량특화성은 ‘왜 차에서 하면 더 좋은가’, 기술 활용성은 ‘그 차이를 실제로 어떻게 구현하는가’에 답한다. 차량 신호를 성공적으로 읽었어도 사용자의 행동이 그대로라면 전자의 근거가 비어 있다. 창의성은 기존 대안과 비교해 새로워진 경험을, 사업성은 그 경험을 원하는 사람을 어떻게 확보하고 다시 쓰게 할지를 본다. [1, 2를 바탕으로 한 팀 해석]

**나중에 적용할 기록법.** 항목마다 ‘주장 한 문장 / 현재 근거 / 아직 검증할 질문’을 남긴다. 예를 들어 사용자 후기는 문제의 존재를, SDK 실행 기록은 구현 가능성을 뒷받침한다. 각각으로 사용 빈도나 재이용 의사까지 입증했다고 쓰지 않는다. 이 기록법은 팀 내부 도구이며 공식 점수표와 구분한다.

**가산점과 2차 심사.** 1차의 앱·에뮬레이터 시연 영상, GitHub 소스·APK는 선택 제출이며 제출 수준에 따라 가산점이 있다. 2차 PT 대상 팀은 실제 동작하는 앱을 준비해야 하며 세부 PT 기준은 추후 안내 대상이다. 숏폼은 별도 특별상이다. [2, 3]

## 일정과 제출

| 날짜 | 팀이 준비할 일 |
|---|---|
| 11월 15일 | 1차 이메일 접수 마감. 지정 접수양식 안에 기획서를 작성하고 참가자 전원이 각각 서명한 동의서를 첨부한다. 대표자가 전원을 참조해 appdevchallenge@hyundai-partners.com 으로 제출한다. |
| 11월 23일 | 서류 결과 발표. 첫 PT까지 열흘이므로 핵심 기능 개발은 미리 진행하는 편이 현실적이다. |
| 12월 3~4일 | 오프라인 PT. 실제 동작 가능한 앱 최종본을 준비해 현장에서 시연한다. |
| 12월 18일 → 2027년 2월 | 수상팀 발표 후 영상·APK 전시 테스트를 준비한다. 그룹 행사에서 전시하고 순위를 공개한다. |

개인 또는 대표 포함 최대 5명이다. 설명회 기준 대학생 부문은 전원이 대학(원)생인 팀이고 일반인이 포함된 팀은 일반 부문이다. 서로 다른 작품은 복수 출품 가능하다. [1, 3, 5]

선택 산출물은 목업·프로토타입 영상과 GitHub 소스·실행 가능한 release APK다. APK는 저장소의 `apk/` 또는 Releases에 두고 README에 앱 소개, 실행법, 테스트 환경, APK 위치를 기재한다. 수정 제출은 같은 주소에서 전체 자료를 다시 보내며 마감 전 마지막 제출본이 심사 대상이다. 설명회 화면과 웹 가이드의 메일 제목 예시에서 앱 이름 포함 여부가 다르므로 발송 직전 공식 안내를 확인한다. [1, 3]

## 개발과 실제 사례

공식 안내 환경은 Java 또는 Kotlin, Android API 28 이상, Gradle 8.0 이상이다. Vehicle SDK는 차량 상태, FusedLocation은 위치, NaviHelper는 길 안내 연동, STT/TTS는 음성 입출력에 대응한다. 필요한 신호의 제공 조건을 개별 SDK 문서에서 확인한다. [4]

별도 부산모빌리티쇼 고객 아이디어 공모에서 약 3,600건 중 선정된 대상작 ‘창밖동화’는 아이와 장거리 이동하는 보호자의 불편을 출발점으로 삼았다. 지나는 지역이 달라지면 들려주는 이야기도 바뀐다. 현대차가 공개한 선정 이유는 타깃과 차량 정보의 쓰임이 분명했다는 것이다. 이번 대회의 주제를 정할 때 비교할 선행 아이디어다. [6]
